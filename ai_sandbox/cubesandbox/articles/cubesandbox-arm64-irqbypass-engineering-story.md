# 从秒级长尾到内核 irqbypass：CubeSandbox ARM64 并发恢复优化记

CubeSandbox 是腾讯云开源的 AI Agent 沙箱服务（[GitHub](https://github.com/tencentcloud/CubeSandbox) · [官网](https://cubesandbox.com)，Apache 2.0 协议），主打极速启动、高并发和安全轻量，为 AI 应用里的代码执行提供隔离环境。

沙箱是为不可信代码准备的隔离执行环境：环境可以联网、可以安装依赖，但不能接触其他用户的数据。在线编程、自动化测试需要这样的环境，AI Agent 兴起后，模型生成的代码同样需要。

极速启动依靠快照恢复。官方把模板（Template）定义为创建沙箱的基础镜像和配置快照：先装好一台虚拟机，在系统和开发环境就绪后对整机状态打快照；之后创建新沙箱不再逐台开机，而是直接从模板快照恢复，省去系统启动和环境准备，官方称之为热启动（Hot Start）。

底座是虚拟机：每台虚拟机自带完整操作系统，隔离比容器更彻底；基于 Rust 虚拟化组件和内核 KVM 构建，对外兼容 AI 沙箱服务 E2B 的 SDK，单沙箱内存开销 5 MB 以内，v0.5 起支持 ARM64 全栈。这次调查恰好发生在 ARM64 服务器上。

单个请求平均 38 毫秒，50 路并发持续创建、累计 500 个请求后，尾部请求要等 5.3 秒——相差百倍。这期间没有任何报错，硬件资源也没有耗尽，吞吐量反而随并发升高而下降：并发 10 时每秒完成 47.9 个请求，并发 50 时只剩 18.4 个。出问题的，正是快照恢复这条路径。

我们排除了应用代码、网络和磁盘的嫌疑，最终锁定的是 Linux 内核里一把不起眼的全局锁。文章完整记录这次追查：我们沿请求路径逐层下钻，看清中断登记框架 irqbypass 中一次链表扫描如何被高并发放大成秒级等待；修复采用内核社区的既有提案方向，高并发复测中 P99 从 5.3 秒回到 350 毫秒。

## 1. 问题出现：单次启动快，高并发出现秒级长尾

2026 年 6 月 22 日，我们对平台做基线压测：并发 1 的单个请求平均 38.2 ms——官方标称 60 ms 内创建，完全达标；并发升到 10，平均延迟 199.2 ms；并发 50、共 500 个请求时，平均延迟 2592.3 ms，99 分位延迟（P99，表示 99% 的成功请求不超过该值）达 5313.2 ms。

系统并非始终缓慢：只有并发升高之后，秒级长尾才会出现。我们由此定下排查方向：问题更像并发请求共同经过某个队列、锁或全局数据结构，而不是每台虚拟机都承担一笔固定的开销。

判断依据很简单：如果固定成本过高，单个请求就会暴露问题；如果只有高并发场景才恶化，说明原本很短的操作大多在共享资源前排队。后续调查围绕“等待在哪里累积”展开。

## 2. 如何测试：先说清请求和指标

5.3 秒从哪来？回答之前，我们先定义这 5.3 秒测量的到底是什么。如果测量口径定义错误，后续的优化就可能偏离目标：把冷启动当成沙箱就绪，或者把平均延迟当作尾部延迟，都会让优化答非所问。

我们采用的口径是“不断创建新沙箱”：每个请求从同一个模板创建一个沙箱，等平台分配资源、恢复虚拟机，收到沙箱内小程序（代理）报告的“就绪”信号后返回；此后不再运行其他任务。每轮先做 3 次预热再正式计数；定位阶段主要用并发 50 的两组规模（共 200 和共 500 次请求），最终对比覆盖并发 10、20 和 50。

官方博客发布过[核心操作的基准报告](https://cubesandbox.com/zh/blog/posts/2026-06-01-cubesandbox-perf-benchmark.html)，覆盖模板创建的启动延迟、并发扩展和单机密度，附完整复现命令。本次调查看的是另一面：同样的操作在高并发下的尾延迟。

两个指标描述结果。延迟是单个请求从发出到创建成功返回的时间：平均延迟反映整体水平，P95 和 P99 分别表示 95% 和 99% 的成功请求不超过对应数值。

吞吐量是整批成功请求数除以整批耗时，描述系统完成请求的速度——不是某个请求延迟的倒数，也不能替代逐请求延迟。

口径的最后一环是边界：我们测的是“从模板创建到沙箱就绪”，既不是虚拟机冷启动，也不是进入沙箱后的首个业务请求。

## 3. 慢在哪里：从端到端一路拆到中断登记

我们的追查从分段计时开始：给创建过程的每一站装上秒表，先观察时间集中在哪个阶段。服务器上的分工并不复杂。一台服务器同时托管许多沙箱虚拟机，一个叫 CubeShim 的软件负责创建、恢复和销毁，并把“从模板恢复虚拟机”这一步记为 `RestoreVm`。

第一轮秒表读数就把范围锁死了：`RestoreVm` 的 P95 与用户看到的创建延迟几乎完全贴合。资源分配和就绪通知只占很小的比例，长尾延迟几乎全部集中在虚拟机恢复阶段。

虚拟机恢复为什么可能慢？答案和普通电脑变慢的原因相通：中断。网卡收到包、磁盘完成读写，都要靠中断——设备有事要报告时发给处理器的信号。虚拟机里的设备由软件模拟，中断的产生、登记和送达同样要软件经手。

我们继续拆分 `RestoreVm`，剩下两个大项：中断控制器的启用、设备恢复。ARM 虚拟机里管理中断的部件叫 VGIC（虚拟通用中断控制器），维护一张路由表，记录宿主机上的每个事件对应虚拟机里的哪个中断。

| 测量阶段 | 并发 50、共 200 次请求 P95 | 并发 50、共 500 次请求 P95 | 读法 |
| --- | ---: | ---: | --- |
| 端到端创建 | 1562.9 ms | 4908.2 ms | 用户看到的长尾 |
| `RestoreVm` | 1520 ms | 4879 ms | 几乎覆盖端到端长尾 |
| VGIC 启用 | 946 ms | 3085 ms | 恢复中的最大热点 |
| 设备恢复 | 745 ms | 1909 ms | 另一条主要支路 |
| 内存快速恢复 | 0 ms | 0 ms | 毫秒精度下不是热点 |

各阶段的 P95 来自不同样本分布，不能直接相加；表格的作用是显示热点随并发增长落在哪些阶段。

进一步拆分后，中断控制器侧的耗时集中在反复登记路由，设备侧则集中在 MSI-X 的恢复。MSI-X 是高速设备（如网卡）采用的中断方案：设备持有一张中断向量表，每一行是一个可独立编号的中断来源，数量可以按需扩展。

我们做了一个诊断实验：把 VGIC 路由表里的传统中断线从 32 条减少到 8 条，以此验证“登记次数放大等待时间”的判断。并发 50、共 500 次请求时，VGIC 启用 P95 从 3085 ms 降到 544.0 ms，设备恢复 P95 仍有 1306.7 ms。

登记数量减少后，等待时间随之下降，这一判断得到验证；设备侧的长尾延迟依然存在，说明还有另一批同类登记没有被发现。

减少中断线数量只用于定位问题，不能作为通用修复方案：不同设备可能需要更多中断线，直接删减存在兼容性风险。调查的下一步，是检查设备恢复中的同类登记操作。

我们又对 2030 个虚拟设备恢复样本做了分段统计：单次总耗时平均 97.784 ms，其中 MSI-X 恢复平均 97.533 ms，其余部分都不超过 1 ms。至此，中断控制和设备两条支路都指向同一种操作：中断的重新登记。

## 4. 内核热点：直通未必生效，登记成本已经发生

两条支路都指向中断登记，追查随之进入内核。中断登记发生在一个冷门框架里，名字叫 irqbypass；框架服务的目标叫中断“直通”：真实硬件设备发出的中断绕过软件中转，直接送进虚拟机，省掉每一步的转发开销。

框架里有两个角色：producer 是发出真实中断的硬件一侧，consumer 是接收中断的虚拟一侧；一张全局登记表记录两侧，配对键（token）是双方共用的标记。硬件和虚拟中断控制器都支持直通、且 token 相同，直通才会建立。

直通是可选的加速，登记是必经的步骤，这也是调查盯住登记成本的原因。登记由 KVM 完成：Linux 内核自带的虚拟化模块，虚拟机的创建、运行和中断注入都由 KVM 负责，CubeSandbox 通过内核接口下达指令。

KVM 里绑定中断的机制叫 irqfd，作用是把 eventfd 和虚拟机的某条中断关联起来。eventfd 是 Linux 里最简单的事件通知对象：宿主机上有人往里写入一个事件，虚拟机里就收到一次中断。每条 irqfd 登记时，KVM 同时把 irqfd 登记为 irqbypass 的 consumer。

登记数量由设备决定。虚拟机里的网卡、磁盘通常是名为 virtio 的虚拟设备，同样使用 MSI-X：一般每个队列分一条中断向量，再留一条报告配置变化。模板快照只保存设备状态，存不下上一次运行时的 eventfd 和中断绑定。

每台虚拟机恢复时，绑定全部重建：CubeSandbox 为每条路由新建 eventfd、分配一个中断编号（GSI）；重放 MSI-X 状态、启用中断组时，逐条调用 `KVM_IRQFD` 登记进 KVM。重放的条件是 MSI-X 总开关打开、没有被整体屏蔽，且只重放未被单独屏蔽的表项。

KVM 收到登记请求后，先装好普通路径：事件到达就唤醒并注入虚拟机；内核启用了 irqbypass 时，再用同一个 eventfd 作为配对键，把 irqfd 登记为接收端。下面的代码按源码顺序摘出关键调用，省略初始化和错误处理。

```c
init_waitqueue_func_entry(&irqfd->wait, irqfd_wakeup);
init_poll_funcptr(&irqfd->pt, irqfd_ptable_queue_proc);
irqfd_update(kvm, irqfd);
list_add_tail(&irqfd->list, &kvm->irqfds.items);

events = vfs_poll(f.file, &irqfd->pt);
if (events & EPOLLIN)
    schedule_work(&irqfd->inject);

if (kvm_arch_has_irq_bypass()) {
    irqfd->consumer.token = (void *)irqfd->eventfd;
    irq_bypass_register_consumer(&irqfd->consumer);
}
```

ARM 服务器的中断控制器叫 GIC。直通要求宿主具备 GICv4.1，或具备 GICv4 且虚拟机启用了虚拟中断转换服务（vITS）；另外要把路由映射到有效的转换目标。

没有匹配的硬件中断来源，或主机不满足直通条件，直通不会建立，中断仍走普通注入路径。接收端的登记和全局表查找，每次照常发生。

![CubeSandbox 模板恢复到 ARM64 中断直通的建立路径](assets/cubesandbox-arm64-irqbypass/restore-to-irqbypass.svg)

本次测试只确认了虚拟设备恢复，没有确认存在配对的硬件设备，因此无法断言直通已经生效。启动成本出在每次恢复必经的登记与查找，而不是直通本身的数据传输。

用户态的秒表到这里已经用尽，剩余热点藏在内核内部，需要换用 `perf lock`——Linux 提供的锁等待观测工具。我们把同样的并发 50、共 200 次负载包进 `perf lock record -a`，再用 `perf lock contention` 按调用点汇总等待时间，KVM 相关互斥锁的排序结果高度集中：

| 热点函数 | 竞争次数 | 累计等待 | 平均等待 | 最大等待 |
| --- | ---: | ---: | ---: | ---: |
| `irq_bypass_register_consumer()` | 6,823 | 1.13 min | 9.92 ms | 57.01 ms |
| `kvm_vgic_map_resources()` | 39 | 2.35 ms | 60.33 µs | 77.71 µs |
| `vgic_its_inject_msi()` | 1 | 3.45 µs | 3.45 µs | 3.45 µs |

其余调用点的竞争次数比首要热点低两个数量级以上。这些数字来自当时保存的汇总，原始数据已无法复查，但 irqbypass 由此成为最主要的怀疑对象。

旧实现用一把模块级互斥锁保护两条全局链表。互斥锁是“同一时间只放一个执行者进门”的锁；登记 consumer 时，持锁扫完 consumer 链表查重复 token，再扫 producer 链表找配对对象。所有虚拟机、设备和中断向量都排在同一把锁上。

没有配对的硬件设备，查重也要扫完不断变长的链表。低并发时这段工作很短；并发恢复大量沙箱时，登记数量和锁内扫描一起增长，后来的请求只能在锁外排队。

至此，三层观察指向同一个结论：端到端分段说明等待发生在虚拟机恢复，登记来源说明大量 irqfd 从哪里来，`perf lock` 给出内核里的共享竞争点。问题从“中断恢复很慢”收敛到全局登记表的查找。

## 5. 补丁做了什么：索引查找替代链表扫描

热点找到后，我们开始动手修复。修复思路很直接：全局互斥锁保持不变，只把锁内的逐项扫描替换为按编号直接查找。

我们先看旧代码，核心行为可以简化为下面几行：两次遍历都在全局锁内进行，链表越长，单次登记需要比较的 token 越多。片段省略了引用计数、返回值和部分错误处理，不是完整源码。

```c
mutex_lock(&lock);
list_for_each_entry(tmp, &consumers, node)
    if (tmp->token == consumer->token)
        goto out;
list_for_each_entry(producer, &producers, node) {
    if (producer->token == consumer->token) {
        if (__connect(producer, consumer))
            goto out;
        break;
    }
}
list_add(&consumer->node, &consumers);
out:
mutex_unlock(&lock);
```

改造使用 XArray：Linux 内核提供的索引容器，按整数编号直接定位对象，类似按页码翻书，不需要从头逐页翻找。token 转换成编号后，查重、插入和跨表匹配都不再逐项扫描。下面同样是省略外围逻辑的机制片段。

```c
mutex_lock(&lock);
index = (unsigned long)consumer->token;
if (xa_load(&consumers, index))
    goto out;
if (xa_insert(&consumers, index, consumer, GFP_KERNEL))
    goto out;
producer = xa_load(&producers, index);
if (producer && __connect(producer, consumer))
    xa_erase(&consumers, index);
out:
mutex_unlock(&lock);
```

![irqbypass 链表与 XArray 注册路径对比](assets/cubesandbox-arm64-irqbypass/list-vs-xarray.svg)

关键点是全局锁仍然保留。改造没有把 irqbypass 变成无锁结构，也没有让连接动作并行执行；唯一的变化是把锁内随对象数量线性增长的查找，换成了按编号的查找。

方向并非原创。把两条链表换成 XArray 的提案，2023 年出现在 [KVM 邮件列表](https://lore.kernel.org/all/20230801115646.33990-1-likexu@tencent.com/)；我们这次做的，是把提案适配进当时使用的 openEuler 6.6 内核，同类改造后来也被 Linux 官方版本收录。

失败路径同样完整：连接失败时，新插入的条目会被删除；登记失败时，先前建好的普通路径照常工作；销毁虚拟机时，KVM 等排队的注入处理完，再注销接收端。

从数量级看，连续登记 N 个没有 producer 的 consumer，旧实现的累计扫描量接近 N 的平方。XArray 消除了逐项遍历，但节点分配、全局串行和连接动作的成本依然存在。

配对的 producer 出现时，连接动作仍在全局锁内执行；ARM64 路径还可能暂停并恢复整台虚拟机。因此，收益应主要来自登记量大的高并发场景，而不是所有恢复步骤都变快。

补丁的边界到此清楚：它优化的是虚拟机恢复期间的登记、匹配和注销；运行期每次中断的注入路径不变，每台虚拟机需要恢复的设备或中断数量也不减少。

## 6. 优化结果：收益随并发放大

补丁生效了吗？我们把改造后的内核换上，重新部署平台、重建模板，用与之前完全相同的口径复测。并发 10、20 和 50 全面改善，并发越高幅度越大；并发 1 没有观察到收益。收益随并发放大的形状，与“缩短全局锁内查找”的机制预期一致。

| 测试规模 | 成功数（旧内核 → 改造后） | 平均延迟（旧内核 → 改造后） | P99（旧内核 → 改造后） | 吞吐量（旧内核 → 改造后） |
| --- | ---: | ---: | ---: | ---: |
| 并发 10、共 200 次请求 | 200/200 → 200/200 | 199.2 → 61.5 ms | 398.4 → 135.5 ms | 47.9 → 143.0 次/秒 |
| 并发 20、共 300 次请求 | 300/300 → 300/300 | 583.3 → 82.8 ms | 1182.5 → 139.3 ms | 33.0 → 214.8 次/秒 |
| 并发 50、共 500 次请求 | 500/500 → 500/500 | 2592.3 → 181.9 ms | 5313.2 → 350.2 ms | 18.4 → 180.5 次/秒 |

最值得关注的不是最高一格的百分比，而是收益随并发递增的形状：数据支持“旧链表扫描是高并发放大器”的解释，不支持“每次恢复的固定成本都下降”的说法。

补丁后的另一轮独立压测复现了同一水平：并发 50、共 500 次请求，平均 172.7 ms，P99 350.3 ms。两次测量互为佐证，改善不是偶然一轮的波动。

这些数字有明确的适用范围：测试在单台 ARM64 主机上进行，内核为 openEuler 24.03 发行版的 Linux 6.6；两轮测试在不同日期进行，中间更换内核并重新部署，不构成严格的单变量对照。数字应读作方向明确的历史观察，而不是可直接推广的承诺。

把这些结果外推到其他环境时同样需要谨慎：其他主机、其他 CubeSandbox 版本或 x86_64 架构上的表现，需要重新验证。成功数只表示创建接口返回成功和测试后完成了清理，不代表沙箱内的业务已经过完整验证。

## 7. 经验与边界：把方法带到下一个问题

回头看，比补丁更值得带走的是一套四步定位法，适用于任何“单次快、并发慢”的性能问题。

第一步，固定操作和指标：模板恢复、冷启动、沙箱就绪和首个业务请求是不同的边界，逐请求延迟、整批耗时和吞吐量也不能互换。第二步，沿真实请求路径逐层计时，每次只拆解当前最大的未知项，让证据保持因果顺序。

第三步，局部改动无效时，转向寻找跨请求共享的锁、队列和登记表：缩小锁范围、批量刷新、调整调用顺序的失败尝试说明，等待只是被移动，并没有被消除。第四步，用并发梯度验证作用域：共享结构的优化应随并发升高而放大，低并发是必要的反例检查。

irqbypass 登记表是 Linux 的通用基础设施，问题只是先在 ARM64 上暴露。这四个步骤可以直接复用；性能数字则必须在新的环境中重新测量。
