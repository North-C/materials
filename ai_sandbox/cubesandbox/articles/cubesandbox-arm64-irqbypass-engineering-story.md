# 一次 CubeSandbox ARM64 并发启动长尾定位

## 1. 问题出现：单次启动快，高并发出现秒级长尾

CubeSandbox 用轻量虚拟机提供隔离沙箱。它支持模板恢复（Template restore）：从预先保存的虚拟机快照恢复沙箱，避免每次都从头启动虚拟机系统。

2026 年 6 月，我们在一台 ARM64 主机上发现：单次创建约为 31.7 ms；并发 200、共 400 次请求时，99 分位延迟（P99）却升到约 3.72 s。P99 表示 99% 的成功请求不超过该值。

系统不是一直慢，而是在并发增长后出现秒级长尾。这改变了排查方向：问题更像是并发请求共同经过某个队列、锁或全局数据结构，而不是每台虚拟机都有一笔固定开销。

如果固定成本过高，单请求就会暴露；如果只有高并发恶化，原本很短的操作很可能在共享资源前排队。后续调查因此围绕“等待在哪里累积”展开。

## 2. 如何测试：先说清请求和指标

测试使用 `create-only`（只创建）工作负载。每个请求都从同一个预制模板（Template）创建沙箱，等平台完成调度、虚拟机恢复，并收到虚拟机内代理的就绪信号后返回；不再执行沙箱内的业务请求。

每轮先做 3 次预热，再以固定并发持续发出请求。定位阶段主要使用并发 50、共 200 次请求和并发 50、共 500 次请求；结果对比还覆盖并发 1、10 和 50。

延迟是单个请求从发出到创建成功返回的时间。平均延迟反映整体水平；P95 和 P99 分别表示 95% 和 99% 的成功请求不超过对应数值。

吞吐量是整批成功请求数除以整批耗时，用来描述系统完成请求的速度。它不是某个请求延迟的倒数，也不能替代逐请求延迟。

这个边界很重要：本文测的是“从 Template 创建到沙箱就绪”，不是虚拟机冷启动，也不是进入沙箱后的首个业务请求。

## 3. 慢在哪里：从端到端一路拆到中断注册

CubeShim 是节点侧负责管理沙箱虚拟机的运行时组件，它把虚拟机恢复阶段记为 `RestoreVm`。第一轮分段先比较这一阶段与用户看到的创建延迟，两者的 P95 几乎贴合。

这说明长尾主要发生在虚拟机恢复阶段，而不是此前的网络、存储调度或此后的就绪通知。调查范围由整条创建链路缩小到了虚拟机内部。

ARM 虚拟机使用虚拟通用中断控制器（VGIC）管理中断状态和路由。这里的路由，是宿主事件与虚拟机中断之间的对应关系。

继续拆分 `RestoreVm`，两个大项正是 VGIC 启用和设备恢复。

| 测量阶段 | 并发 50、共 200 次请求 P95 | 并发 50、共 500 次请求 P95 | 读法 |
| --- | ---: | ---: | --- |
| 端到端创建 | 1562.9 ms | 4908.2 ms | 用户看到的长尾 |
| `RestoreVm` | 1520 ms | 4879 ms | 几乎覆盖端到端长尾 |
| VGIC 启用 | 946 ms | 3085 ms | 恢复中的最大热点 |
| 设备恢复 | 745 ms | 1909 ms | 另一条主要支路 |
| 内存快速恢复 | 0 ms | 0 ms | 毫秒精度下不是热点 |

各阶段的 P95 来自不同样本分布，不能直接相加；它们的作用是显示热点随并发增长落在哪些阶段。

继续拆分后，VGIC 的主要耗时落在重复注册中断路由。设备侧则集中在 MSI-X 恢复。MSI-X 让 PCIe 设备使用多条独立的中断向量；每条向量代表一个可单独路由的中断来源。

基于 PCI 的 virtio 设备通常为队列分配多条向量，并为配置变化再保留一条。因此，恢复一台虚拟机可能触发多次中断注册。

恢复快照时，MSI-X 表、掩码和启用状态可以读回，但宿主机上的文件描述符和 KVM 路由不能直接复用。所谓 irqfd，是 KVM 用来重新建立这些资源的中断绑定接口。

irqfd 把 eventfd 这种 Linux 事件通知对象，与虚拟机中断路由关联起来，让宿主事件能够触发虚拟机中断。恢复代码只在 MSI-X 整体已启用且功能级掩码关闭时，重放未被单独屏蔽的表项。

这一步把 CubeSandbox 启动沙箱和 Linux 的中断直通配对框架 irqbypass 连了起来。模板快照只能保存设备与中断控制器的状态，不能保存上一次运行时的 eventfd 和 KVM 路由。重建设备时，CubeSandbox 为中断组内每条路由新建 eventfd、分配全局系统中断号（GSI）；重放 MSI-X 状态并启用中断组时，再逐条调用 `KVM_IRQFD` 注册。

KVM 收到 `KVM_IRQFD` 后，先安装普通 irqfd 的唤醒和注入路径。随后，只要当前架构启用了 irqbypass，KVM 就会用同一个 eventfd 作为配对键，把这条 irqfd 登记为 irqbypass 的接收端。

下面的代码按源码顺序摘出关键调用，省略了字段初始化、回调赋值和错误处理。它保留了先建立普通路径、再登记 irqbypass 的关系，并不代表完整实现。

```c
init_waitqueue_func_entry(&irqfd->wait, irqfd_wakeup);
init_poll_funcptr(&irqfd->pt, irqfd_ptable_queue_proc);
irqfd_update(kvm, irqfd);
list_add_tail(&irqfd->list, &kvm->irqfds.items);

events = vfs_poll(f.file, &irqfd->pt);
if (events & EPOLLIN)
    schedule_work(&irqfd->inject);

if (kvm_arch_has_irq_bypass()) {
    irqfd->consumer.token = (void *)irqfd->eventfd;
    irq_bypass_register_consumer(&irqfd->consumer);
}
```

irqbypass 接下来会查找使用同一配对键的硬件中断来源。ARM64 上，宿主具备 GICv4.1，或具备 GICv4 且虚拟机启用了虚拟中断转换服务（vITS），KVM 才满足直接 MSI 转发的控制器条件；此外还要把路由映射到有效的虚拟中断转换目标。

如果没有匹配的硬件中断来源，或者主机不满足直通条件，就不会建立中断直通，普通 irqfd 路径仍然可用。但 irqbypass 的接收端登记和全局表查找已经发生。

```mermaid
flowchart TD
    A[从模板恢复沙箱] --> B[恢复 VGIC 和 virtio-pci 设备]
    B --> C[每条 MSI-X 路由新建 eventfd 和 GSI]
    C --> D[重放已启用且未屏蔽的 MSI-X 表项]
    D --> E[启用中断组并逐路由调用 KVM_IRQFD]
    E --> F[建立普通 irqfd 注入路径]
    F --> G[登记 irqbypass 接收端]
    G --> H{同一 eventfd 配对键下有硬件中断来源?}
    H -- 否 --> J[继续使用普通 irqfd 路径]
    H -- 是 --> K{GICv4.1 或 GICv4 加 vITS 且路由有效?}
    K -- 是 --> I[建立直接 MSI 转发]
    K -- 否 --> J
```

这次测试记录只确认了虚拟设备恢复，没有确认同一配对键下存在硬件中断来源，也不能断言直接 MSI 转发生效。历史证据指向的启动成本，是每次恢复必经的 irqbypass 登记和全局表查找，而不是硬件直通的数据面开销。

一次诊断把 VGIC 的旧式中断路由数从 32 减到 8。并发 50、共 500 次请求时，VGIC 启用 P95 从 3085 ms 降到 544.0 ms，而设备恢复 P95 仍有 1306.7 ms。

阶段时间随注册数量下降，支持“注册次数会放大等待”的判断；设备侧长尾仍然存在，说明还需寻找另一批同类注册。

这项改动只用于定位，不能作为通用修复。不同设备可能需要更多路由，直接删减会带来兼容性风险。它进一步验证了注册数量与等待有关，下一步应继续检查设备恢复中的同类操作。

对 2030 个 virtio-pci 设备恢复样本再分段，单次总耗时平均 97.784 ms，其中 MSI-X 恢复平均 97.533 ms，其余部分均不超过 1 ms。VGIC 和设备两条支路至此都指向 irqfd 注册。

## 4. 内核热点：直通未必生效，注册成本已经发生

irqbypass 是 Linux 内核管理中断直通配对的框架。它维护一张全局注册表：producer 是发出宿主中断的一侧，consumer 是接收中断的一侧；上一节中的 KVM irqfd 会注册为 consumer。

两侧使用同一个 token，也就是配对键。只有硬件和虚拟中断控制器都支持直接转发，并且 token 相同，才会建立直通连接；否则普通 irqfd 注入路径仍然可用。

历史工作负载并未确认存在硬件 producer。因此，这次定位关注的是启动期间 consumer 进入全局注册表的管理成本，而不是硬件直通生效后的数据传输收益。

`perf lock` 是 Linux 用来观察锁等待的性能工具。在并发 50、共 200 次请求的一次采样中，KVM 相关互斥锁（mutex）的突出调用点是 irqbypass 的 `irq_bypass_register_consumer()`。

| 热点函数 | 竞争次数 | 累计等待 | 平均等待 | 最大等待 |
| --- | ---: | ---: | ---: | ---: |
| `irq_bypass_register_consumer()` | 6,823 | 1.13 min | 9.92 ms | 57.01 ms |

这组数字来自当时保存的汇总，原始 `perf` 数据已无法复查，宿主内核也没有启用更细的锁统计。它足以把 irqbypass 提升为首要假设，但不能单独证明唯一根因。

旧实现用一把模块级 mutex 保护 producer 和 consumer 两条全局链表。注册 consumer 时，持锁扫描 consumer 链表检查重复 token，再扫描 producer 链表寻找配对对象。不同虚拟机、设备和向量都会经过同一把锁。

即使没有匹配的硬件 producer，consumer 的重复检查仍要扫描不断增长的全局链表。低并发时这段工作很短；并发恢复大量沙箱时，注册数量和锁内扫描同时增长，后续请求开始在 mutex 外排队。

端到端分段说明等待发生在虚拟机恢复，MSI-X 分段说明大量 irqfd 注册从哪里来，`perf lock` 则给出了内核里的共享竞争点。三层观察把问题从“中断恢复很慢”收敛到全局注册表查找。

## 5. 补丁做了什么：索引查找替代链表扫描

旧代码的核心行为可以简化为下面几行。两次遍历都发生在全局 mutex 内，链表越长，单次注册需要比较的 token 越多。为突出查找路径，片段省略了引用计数、返回值和部分错误处理，不是完整源码。

```c
mutex_lock(&lock);
list_for_each_entry(tmp, &consumers, node)
    if (tmp->token == consumer->token)
        goto out;
list_for_each_entry(producer, &producers, node) {
    if (producer->token == consumer->token) {
        if (__connect(producer, consumer))
            goto out;
        break;
    }
}
list_add(&consumer->node, &consumers);
out:
mutex_unlock(&lock);
```

改造使用 XArray。XArray 是 Linux 内核的索引容器，可以按整数索引定位对象。token 指针转换成索引后，重复检查、插入和跨表匹配不再需要逐项扫描。下面同样是省略外围逻辑的机制片段。

```c
mutex_lock(&lock);
index = (unsigned long)consumer->token;
if (xa_load(&consumers, index))
    goto out;
if (xa_insert(&consumers, index, consumer, GFP_KERNEL))
    goto out;
producer = xa_load(&producers, index);
if (producer && __connect(producer, consumer))
    xa_erase(&consumers, index);
out:
mutex_unlock(&lock);
```

```mermaid
flowchart LR
    subgraph O[旧链表]
        O1[全局 mutex] --> O2[扫描 consumer 链表]
        O2 --> O3[扫描 producer 链表]
        O3 --> O4[匹配并连接]
    end
    subgraph N[改造后]
        N1[同一全局 mutex] --> N2[XArray 按 token 查找]
        N2 --> N3[匹配并连接]
    end
```

关键点是全局 mutex 仍然保留。改造没有把 irqbypass 变成无锁结构，也没有让连接回调并行执行；它只把锁内随对象数量线性增长的查找，换成按 token 索引的查找。

连接失败时，新插入的 XArray 条目会被删除。irqbypass 注册失败时，KVM 先前建立的普通 irqfd 路径仍可工作；销毁虚拟机时，KVM 会等待已排队的注入结束，再注销 consumer。

连续注册 N 个没有 producer 的 consumer 时，旧实现的累计重复扫描可接近 N 的平方。XArray 消除了这项线性遍历，但节点分配、全局串行和连接回调仍有成本。

如果出现匹配的 producer，连接回调仍在全局 mutex 内执行；ARM64 路径还可能暂停并恢复整台虚拟机。因此，收益应主要来自注册量大的高并发场景，而不是所有恢复步骤都变快。

这也是补丁的功能边界：它优化虚拟机恢复期间的 irqfd 注册、匹配和注销，不改变运行期每次中断的注入路径，也不减少每台虚拟机需要恢复的设备或中断向量数量。

## 6. 优化结果：收益随并发放大

改造内核后，测试仍按相同的请求口径统计。低并发没有观察到收益；并发 10 和 50 时，平均延迟、P99 和吞吐量都明显改善。这种并发选择性与“缩短全局锁内查找”这一机制预期一致。

| 测试规模 | 成功数（旧内核 → 改造后） | 平均延迟（旧内核 → 改造后） | P99（旧内核 → 改造后） | 吞吐量（旧内核 → 改造后） |
| --- | ---: | ---: | ---: | ---: |
| 并发 1、共 20 次请求 | 20/20 → 20/20 | 38.2 → 45.2 ms | 47.6 → 91.3 ms | 22.5 → 19.4 次/秒 |
| 并发 10、共 200 次请求 | 200/200 → 200/200 | 199.2 → 61.5 ms | 398.4 → 135.5 ms | 47.9 → 143.0 次/秒 |
| 并发 50、共 500 次请求 | 500/500 → 500/500 | 2592.3 → 181.9 ms | 5313.2 → 350.2 ms | 18.4 → 180.5 次/秒 |

最值得关注的不是最高并发的一项百分比，而是低并发与高并发的差异。它支持“旧链表扫描是高并发放大器”，却不支持“每次恢复的固定成本都下降”。

并发 1 的单轮结果反而变慢。由于没有重复测量和误差范围，不能据此断言改造在低并发下必然回退；可靠的结论只是“低并发没有观察到收益”。

这些数据来自单台 ARM64 主机和 openEuler 6.6。两轮测试发生在不同日期，中间更换内核、重新部署并新建 Template，不是随机交替、多轮重复的严格单变量对照。

因此，表格展示的是方向明确的历史观察，不是可直接推广的性能承诺。成功数只表示创建接口返回成功和测试后完成清理，不代表虚拟机内网络、存储和数据一致性都经过完整验证。

当时临时补丁和内核包的精确二进制身份已无法恢复，改造后也没有保存可用的 `perf lock` 复采。因此，现有证据不能证明锁热点已经消失。

前后两轮还包含重新部署等环境变化，改善不能归因于唯一因素。这些数字也不能直接外推到其他主机、CubeSandbox 版本或 x86_64。

## 7. 经验与边界：把方法带到下一个问题

第一步永远是固定操作和指标。模板恢复、虚拟机冷启动、沙箱就绪和首个业务请求是不同边界；逐请求延迟、整批耗时和吞吐量也不能互换。边界不清，后面的优化很容易答非所问。

第二步是沿真实请求路径逐层计时。端到端数据先把范围压到虚拟机恢复，阶段数据再分出 VGIC 和设备，设备数据又落到 MSI-X。每次只拆当前最大的未知项，调查才能保持因果顺序。

缩小用户态锁范围、批量刷新和调整调用顺序等尝试没有解决长尾，却提供了重要信息：当局部改动只是移动等待，应继续寻找跨虚拟机共享的锁、队列和注册表，而不是反复微调同一段代码。

最后要用并发梯度验证作用域。共享结构优化应在高并发更明显，低并发则是必要的反例检查。若结果不随并发变化，就应重新审视热点与优化之间的因果关系。

这次问题是在 ARM64 环境中发现的，但 irqbypass 注册表属于 Linux 通用基础设施，并非 ARM64 专属。可以迁移的是“分层计时、改变注册规模、观察锁竞争、再用并发梯度复测”的方法，而不是某一组性能数字。
