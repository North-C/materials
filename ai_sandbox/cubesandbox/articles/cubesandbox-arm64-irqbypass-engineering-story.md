# 从秒级长尾到内核 irqbypass：CubeSandbox ARM64 并发恢复优化记

这是一次性能调查的完整还原：高并发创建沙箱时延迟涨到秒级，我们沿请求路径逐层计时，把热点一路追到 Linux 内核 irqbypass 框架里的一把全局锁。

修复方向来自社区邮件列表上的提案，验证依靠并发梯度复测。文章不要求沙箱或 CubeSandbox 背景，涉及的虚拟化和内核概念都会随文解释；如果你面对的也是“单次很快、并发才慢”的问题，这套方法可以直接搬用。

## 1. 问题出现：单次启动快，高并发出现秒级长尾

在线编程、自动化测试这类服务，经常要运行来自用户的代码；AI Agent 兴起后，模型生成的代码同样需要在隔离环境里执行。这些代码不可信任——环境既要能联网、能装依赖，又不能碰其他用户的数据。这样的隔离环境通常叫沙箱。

CubeSandbox 是腾讯云的开源项目（Apache 2.0 协议），[代码托管在 GitHub](https://github.com/tencentcloud/CubeSandbox)，[文档与动态见官方网站](https://cubesandbox.com)。官方对它的定位是“极速启动、高并发、安全且轻量化的 AI Agent 沙箱服务”，专门为 AI 应用里的代码执行提供隔离环境。

从官方资料看，它用虚拟机实现沙箱：每台虚拟机自带完整的操作系统，隔离比容器更彻底；底层基于 Rust 虚拟化组件和内核 KVM 构建，对外兼容 AI 沙箱服务 E2B 的 SDK。官方公布的指标是 60 ms 内创建一个硬件级隔离的沙箱、单沙箱内存开销 5 MB 以内，并从 v0.5 起支持 ARM64 全栈——本文的调查恰好发生在 ARM64 服务器上。

它的速度主要来自“读档”：官方把模板（Template）定义为创建沙箱的基础镜像和配置快照——先装好一台虚拟机并拍下快照，之后每个新沙箱都从模板热启动，相当于游戏读档，跳过开机和装环境。本文的问题，正出在这个从模板恢复的动作上。

2026 年 6 月初的一轮压测里，单个请求创建沙箱约 31.7 ms；同一环境把并发加到 200、总共 400 个请求后，99 分位延迟（P99）升到约 3.72 s。P99 表示 99% 的成功请求不超过该值。

系统不是一直慢，而是并发涨上去之后才出现秒级长尾。这决定了排查方向：问题更像并发请求共同经过某个队列、锁或全局数据结构，而不是每台虚拟机都背着一笔固定开销。

如果固定成本过高，单请求就会暴露；如果只有高并发恶化，原本很短的操作多半在共享资源前排队。后续调查因此围绕“等待在哪里累积”展开。

## 2. 如何测试：先说清请求和指标

测试模拟的真实用法是“不断创建新沙箱”。每个请求都从同一个模板创建一个沙箱，等平台分配资源、恢复虚拟机，并收到沙箱内小程序（代理）报告的“就绪”信号后返回；此后不再运行其他任务。

这样测出来的就是“创建沙箱”本身的速度，不含沙箱里跑的业务。每轮先做 3 次预热再正式计数；定位阶段主要用并发 50 的两组规模（共 200 和共 500 次请求），最终对比覆盖并发 10、20 和 50。

这不是 CubeSandbox 第一次被量化：官方博客发布过核心操作的基准报告，覆盖模板创建的启动延迟、并发扩展和单机密度，并附完整复现命令（[报告链接](https://cubesandbox.com/zh/blog/posts/2026-06-01-cubesandbox-perf-benchmark.html)）。本文看的是它的另一面——同样的操作在高并发下的尾延迟。

延迟是单个请求从发出到创建成功返回的时间。平均延迟反映整体水平；P95 和 P99 分别表示 95% 和 99% 的成功请求不超过对应数值。

吞吐量是整批成功请求数除以整批耗时，描述系统完成请求的速度。它不是某个请求延迟的倒数，也不能替代逐请求延迟。

这个边界很重要：本文测的是“从模板创建到沙箱就绪”，不是虚拟机冷启动，也不是进入沙箱后的首个业务请求。

## 3. 慢在哪里：从端到端一路拆到中断登记

要看懂定位过程，先记住服务器上的分工：一台服务器同时托管许多沙箱虚拟机；服务器上有个负责创建、恢复、销毁这些虚拟机的软件（CubeShim），它把“从模板恢复虚拟机”这一步记为 `RestoreVm`。

第一轮分段比较了 `RestoreVm` 与用户看到的创建延迟，两者的 P95 几乎贴合。这说明长尾主要发生在虚拟机恢复阶段，而不是此前的资源分配，或此后的就绪通知。

虚拟机恢复为什么可能慢？每台虚拟机都是一台完整的小电脑：网卡收到包、磁盘完成读写，都要靠中断——设备有事要报告时发给处理器的信号。虚拟机里的设备是软件模拟的，中断的产生、登记和送达同样要软件经手。

继续拆分 `RestoreVm`，剩下两个大项：中断控制器的启用和设备恢复。ARM 虚拟机里管理中断的部件叫 VGIC（虚拟通用中断控制器），它维护一张路由表，记录宿主机上的每个事件对应虚拟机里的哪个中断。

| 测量阶段 | 并发 50、共 200 次请求 P95 | 并发 50、共 500 次请求 P95 | 读法 |
| --- | ---: | ---: | --- |
| 端到端创建 | 1562.9 ms | 4908.2 ms | 用户看到的长尾 |
| `RestoreVm` | 1520 ms | 4879 ms | 几乎覆盖端到端长尾 |
| VGIC 启用 | 946 ms | 3085 ms | 恢复中的最大热点 |
| 设备恢复 | 745 ms | 1909 ms | 另一条主要支路 |
| 内存快速恢复 | 0 ms | 0 ms | 毫秒精度下不是热点 |

各阶段的 P95 来自不同样本分布，不能直接相加；它们的作用是显示热点随并发增长落在哪些阶段。

再往细拆，中断控制器侧的耗时集中在反复登记路由；设备侧集中在 MSI-X 的恢复。MSI-X 是高速设备（如网卡）的中断方案：设备持有一张向量表，每行都是一个可独立编号的中断来源，要多少行加多少行。

为了验证“登记次数放大等待”，我们做过一次诊断性修改：把 VGIC 路由表里的传统中断线从 32 条减到 8 条。并发 50、共 500 次请求时，VGIC 启用 P95 从 3085 ms 降到 544.0 ms，设备恢复 P95 仍有 1306.7 ms。

登记数量减少，等待随之下降，假设得到了支持；设备侧长尾仍在，说明还有另一批同类登记没被找到。

这项改动只用于定位，不能当作通用修复：不同设备可能需要更多中断线，直接删减有兼容性风险。下一步该检查设备恢复里的同类登记。

对 2030 个虚拟设备恢复样本再分段，单次总耗时平均 97.784 ms，其中 MSI-X 恢复平均 97.533 ms，其余部分都不超过 1 ms。中断控制和设备两条支路，至此都指向同一种操作：中断的重新登记。

## 4. 内核热点：直通未必生效，登记成本已经发生

上一节反复出现的中断登记，在内核里由一个专门框架管理，叫 irqbypass。它服务的目标是中断“直通”：让真实硬件设备发出的中断绕过软件中转，直接送进虚拟机，省掉每一步的转发开销。

框架里有两个角色：producer 是发出真实中断的硬件一侧，consumer 是接收中断的虚拟一侧；一张全局登记表记录两侧，配对键（token）是双方共用的标记。只有硬件和虚拟中断控制器都支持直通、且 token 相同，直通才会建立。

直通是可选的加速，登记是必经的步骤——这正是本文关注登记成本的原因。而登记的入口是 KVM：Linux 内核自带的虚拟化模块，虚拟机的创建、运行和中断注入都由它完成，CubeSandbox 通过内核接口向它下指令。

KVM 里用来绑定中断的机制叫 irqfd：把 eventfd——Linux 里最简单的事件通知对象——和虚拟机的某条中断关联起来。宿主机上有人往 eventfd 写入一个事件，虚拟机里就收到一次中断；每条 irqfd 登记时，KVM 都会把它登记为 irqbypass 的 consumer。

登记的数量由设备决定。虚拟机里的网卡、磁盘通常是名为 virtio 的虚拟设备，同样使用 MSI-X：一般每个队列分一条中断向量，再留一条报告配置变化。而模板快照只保存设备状态，存不下上一次运行时的 eventfd 和中断绑定。

因此每台虚拟机恢复时，这些绑定都要重建：CubeSandbox 为每条路由新建 eventfd、分配一个中断编号（GSI）；重放 MSI-X 状态、启用中断组时，再逐条调用 `KVM_IRQFD` 登记进 KVM。重放的条件是 MSI-X 总开关打开、没有被整体屏蔽，且只重放未被单独屏蔽的表项。

KVM 收到登记请求后，先装好普通路径——事件到达就唤醒并注入虚拟机；只要内核启用了 irqbypass，再用同一个 eventfd 作为配对键，把这条 irqfd 登记为接收端。下面的代码按源码顺序摘出关键调用，省略了初始化和错误处理。

```c
init_waitqueue_func_entry(&irqfd->wait, irqfd_wakeup);
init_poll_funcptr(&irqfd->pt, irqfd_ptable_queue_proc);
irqfd_update(kvm, irqfd);
list_add_tail(&irqfd->list, &kvm->irqfds.items);

events = vfs_poll(f.file, &irqfd->pt);
if (events & EPOLLIN)
    schedule_work(&irqfd->inject);

if (kvm_arch_has_irq_bypass()) {
    irqfd->consumer.token = (void *)irqfd->eventfd;
    irq_bypass_register_consumer(&irqfd->consumer);
}
```

ARM 服务器的中断控制器叫 GIC。直通要求宿主具备 GICv4.1，或具备 GICv4 且虚拟机启用了虚拟中断转换服务（vITS）；此外还要把路由映射到有效的转换目标。

如果没有匹配的硬件中断来源，或主机不满足直通条件，直通不会建立，中断仍走普通注入路径。但接收端的登记和全局表查找，每次都会照常发生。

![CubeSandbox 模板恢复到 ARM64 中断直通的建立路径](assets/cubesandbox-arm64-irqbypass/restore-to-irqbypass.svg)

这次测试只确认了虚拟设备恢复，没有确认存在配对的硬件设备，因此不能断言直通生效。启动成本出在每次恢复必经的登记与查找，而不是直通本身的数据传输。

`perf lock` 是 Linux 观察锁等待的工具。把同样的并发 50、共 200 次负载用 `perf lock record -a` 包住，再用 `perf lock contention` 按调用点汇总等待时间，KVM 相关互斥锁的排序结果非常集中：

| 热点函数 | 竞争次数 | 累计等待 | 平均等待 | 最大等待 |
| --- | ---: | ---: | ---: | ---: |
| `irq_bypass_register_consumer()` | 6,823 | 1.13 min | 9.92 ms | 57.01 ms |
| `kvm_vgic_map_resources()` | 39 | 2.35 ms | 60.33 µs | 77.71 µs |
| `vgic_its_inject_msi()` | 1 | 3.45 µs | 3.45 µs | 3.45 µs |

其余调用点的竞争次数比首要热点少两个数量级以上。这组数字来自当时保存的汇总，原始数据已无法复查，但它足以把 irqbypass 提升为首要假设。

旧实现用一把模块级互斥锁保护两条全局链表。互斥锁是“同一时间只放一个执行者进门”的锁；登记 consumer 时，持锁扫完 consumer 链表查重复 token，再扫 producer 链表找配对对象。所有虚拟机、设备和中断向量都排在同一把锁上。

即使没有配对的硬件设备，查重也要扫完不断变长的链表。低并发时这段工作很短；并发恢复大量沙箱时，登记数量和锁内扫描一起增长，后来的请求只能在锁外排队。

端到端分段说明等待发生在虚拟机恢复，登记来源说明大量 irqfd 从哪里来，`perf lock` 给出内核里的共享竞争点。三层观察把问题从“中断恢复很慢”收敛到全局登记表的查找。

## 5. 补丁做了什么：索引查找替代链表扫描

旧代码的核心行为可以简化为下面几行。两次遍历都发生在全局锁内，链表越长，单次登记需要比较的 token 越多。为突出查找路径，片段省略了引用计数、返回值和部分错误处理，不是完整源码。

```c
mutex_lock(&lock);
list_for_each_entry(tmp, &consumers, node)
    if (tmp->token == consumer->token)
        goto out;
list_for_each_entry(producer, &producers, node) {
    if (producer->token == consumer->token) {
        if (__connect(producer, consumer))
            goto out;
        break;
    }
}
list_add(&consumer->node, &consumers);
out:
mutex_unlock(&lock);
```

改造使用 XArray——Linux 内核的索引容器，可以按整数编号直接定位对象，类似按页码翻书，而不是从头逐页翻找。token 转换成编号后，查重、插入和跨表匹配都不再逐项扫描。下面同样是省略外围逻辑的机制片段。

```c
mutex_lock(&lock);
index = (unsigned long)consumer->token;
if (xa_load(&consumers, index))
    goto out;
if (xa_insert(&consumers, index, consumer, GFP_KERNEL))
    goto out;
producer = xa_load(&producers, index);
if (producer && __connect(producer, consumer))
    xa_erase(&consumers, index);
out:
mutex_unlock(&lock);
```

![irqbypass 链表与 XArray 注册路径对比](assets/cubesandbox-arm64-irqbypass/list-vs-xarray.svg)

关键点是全局锁仍然保留。改造没有把 irqbypass 变成无锁结构，也没有让连接动作并行执行；它只把锁内随对象数量线性增长的查找，换成按编号的查找。

这个方向并非我们首创。把两条链表换成 XArray 的提案，2023 年就出现在 [KVM 邮件列表](https://lore.kernel.org/all/20230801115646.33990-1-likexu@tencent.com/)上；我们做的是把它适配进当时使用的 openEuler 6.6 内核，同类改造后来也被 Linux 官方版本收录。想了解设计权衡的读者，可以从原始讨论读起。

连接失败时，新插入的条目会被删除。登记失败时，先前建好的普通路径仍可工作；销毁虚拟机时，KVM 会等排队的注入处理完，再注销接收端。

连续登记 N 个没有 producer 的 consumer 时，旧实现的累计扫描可接近 N 的平方。XArray 消除了这项逐项遍历，但节点分配、全局串行和连接动作仍有成本。

如果出现配对的 producer，连接动作仍在全局锁内执行；ARM64 路径还可能暂停并恢复整台虚拟机。因此收益应主要来自登记量大的高并发场景，而不是所有恢复步骤都变快。

这也是补丁的功能边界：它优化虚拟机恢复期间的登记、匹配和注销，不改变运行期每次中断的注入路径，也不减少每台虚拟机需要恢复的设备或中断数量。

## 6. 优化结果：收益随并发放大

换上改造后的内核，平台重新部署、模板重新创建，按相同口径复测。并发 10、20 和 50 时，平均延迟、P99 和吞吐量都明显改善，且并发越高改善越大；并发 1 没有观察到收益。这种随并发放大的选择性与“缩短全局锁内查找”的机制预期一致。

| 测试规模 | 成功数（旧内核 → 改造后） | 平均延迟（旧内核 → 改造后） | P99（旧内核 → 改造后） | 吞吐量（旧内核 → 改造后） |
| --- | ---: | ---: | ---: | ---: |
| 并发 10、共 200 次请求 | 200/200 → 200/200 | 199.2 → 61.5 ms | 398.4 → 135.5 ms | 47.9 → 143.0 次/秒 |
| 并发 20、共 300 次请求 | 300/300 → 300/300 | 583.3 → 82.8 ms | 1182.5 → 139.3 ms | 33.0 → 214.8 次/秒 |
| 并发 50、共 500 次请求 | 500/500 → 500/500 | 2592.3 → 181.9 ms | 5313.2 → 350.2 ms | 18.4 → 180.5 次/秒 |

最值得关注的不是最高并发那格的百分比，而是收益随并发递增的形状：它支持“旧链表扫描是高并发放大器”，不支持“每次恢复的固定成本都下降”。

这些数据来自单台 ARM64 主机，内核为 openEuler 24.03 发行版的 Linux 6.6。两轮测试在不同日期进行，中间更换内核并重新部署，不是严格的单变量对照；数字应读作方向明确的历史观察，而不是可直接推广的承诺。

外推同样要谨慎：其他主机、其他 CubeSandbox 版本或 x86_64 上的表现，需要重新验证。成功数只表示创建接口返回成功和测试后清理完成，不代表沙箱内业务已完整验证。

## 7. 经验与边界：把方法带到下一个问题

第一步永远是固定操作和指标。模板恢复、虚拟机冷启动、沙箱就绪和首个业务请求是不同边界；逐请求延迟、整批耗时和吞吐量也不能互换。边界不清，后面的优化很容易答非所问。

第二步是沿真实请求路径逐层计时。端到端数据把范围压到虚拟机恢复，阶段数据分出中断控制和设备，设备数据落到 MSI-X。每次只拆当前最大的未知项，调查才能保持因果顺序。

缩小锁的范围、批量刷新和调整调用顺序等尝试没有解决长尾，却提供了重要信息：当局部改动只是移动等待，就应该去找跨虚拟机共享的锁、队列和登记表，而不是反复微调同一段代码。

最后用并发梯度验证作用域。共享结构的优化应在高并发更明显，低并发则是必要的反例检查。若结果不随并发变化，就该重新审视热点与优化之间的因果关系。

这次问题是在 ARM64 服务器上发现的，但 irqbypass 登记表是 Linux 通用基础设施，并非 ARM64 专属。可以迁移的是“分层计时、改变登记规模、观察锁竞争、再用并发梯度复测”这套方法，而不是某一组数字。
